# Glossary

Canonical domain terms for **Zero-Restart Pod Rightsizing on GKE 1.37** (`gke-demos/pod-rightsizing`).

| Term | Definition | Avoid |
| :--- | :--- | :--- |
| **CPU Startup Boost** | Configuring `spec.startupBoost.cpu` (`type: "Factor"` or `"Quantity"`, `durationSeconds`) on a GKE `VerticalPodAutoscaler` (`autoscaling.k8s.io/v1` in GKE `1.36.0-gke.4447000+`) so the VPA admission webhook temporarily increases a container's CPU request and limit during initialization. | "Startup overclock", "init container boost". |
| **Admission Boost Annotation (`vpaCPUStartupBoost`)** | The Pod metadata annotation (`vpaCPUStartupBoost/<container-name>`, alongside `vpaObservedContainers` and `vpaUpdates`) injected by the GKE VPA admission webhook (`gke-vpa-webhook-config`) at Pod creation time that records the container's baseline `requests` and `limits` JSON before applying the boosted CPU allocation. Note that GKE 1.37's admission controller uses uppercase `CPU` (`vpaCPUStartupBoost`), whereas some documentation examples spell it `vpaCpuStartupBoost`. | "Boost label". |
| **In-Place Unboost** | The phase after a boosted Pod reaches `Ready` and `durationSeconds` elapses in which the GKE VPA Updater resizes the container's CPU request and limit back to its baseline values **in-place** (`restartCount: 0`), removes the `vpaCPUStartupBoost/<container-name>` annotation, and emits a Kubernetes event with `reason=InPlaceResizedByVPA`. | "Downscale restart", "Pod recreation". |
| **In-Place Pod Resize (IPPR)** | Kubernetes capability (GA in GKE `1.35+`, exposed in VPA via `spec.updatePolicy.updateMode: "InPlaceOrRecreate"`) that mutates a running container's Linux cgroup CPU and memory allocations without restarting the container or evicting the Pod. | "Hot swap", "live recreate". |
| **Startup Throttling (`nr_throttled`)** | Linux CFS bandwidth throttling (`nr_throttled` and `throttled_usec` in `/sys/fs/cgroup/cpu.stat`) experienced by an initialization-heavy container when its steady-state CPU limit (`limits.cpu`) restricts CPU burst capacity during cold start. | "CPU starvation". |
| **Cooperative VPA + HPA Rightsizing** | Setting the annotation `gke.io/autoscaling-hpa-rightsizing-mode: "gke-hpa-rightsizing-mode-policy"` on a `VerticalPodAutoscaler` (`1.36.3-gke.1630000+`) alongside an `autoscaling/v2` CPU `HorizontalPodAutoscaler` so HPA scales replica counts horizontally for traffic spikes while VPA rightsizes per-replica CPU requests based on historical aggregate demand and HPA bounds (`minReplicas`, `maxReplicas`, `averageUtilization`). | "Dual autoscaling", "competing autoscalers". |
| **HPA Startup Spillover Trap** | Premature horizontal scale-out triggered when a Pod's high startup CPU usage continues after the Pod transitions to `Ready` and is counted by HPA; prevented by defining a `readinessProbe` that only succeeds after initialization completes and setting `startupBoost.cpu.durationSeconds: 0`. | "False scale-out". |
| **Partial Teardown Footgun** | Removing only the `gke.io/autoscaling-hpa-rightsizing-mode` annotation from a `VerticalPodAutoscaler` while leaving `spec.updatePolicy.updateMode` set to `"InPlaceOrRecreate"` or `"Recreate"`, which reverts VPA to standard non-cooperative mode and causes VPA and HPA to fight over CPU utilization. | "Unannotating VPA". |
| **VPA Decision Audit Logs (`KCP_VPA`)** | Control-plane VPA decision events exported to Cloud Logging (`logName="projects/<PROJECT_ID>/logs/container.googleapis.com%2Fvpa-controller"`) when `--logging=SYSTEM,KCP_VPA` is enabled on a GKE `1.36.0-gke.1601000+` cluster. | "VPA pod logs". |
| **Rightsizing Inspector** | The zero-build demo workload (`Deployment/throttled-app` and `Deployment/boosted-app`) that performs deterministic CPU-bound initialization before `/readyz` returns `200 OK` and exposes live cgroup v2 CPU allocation (`cpu.max` / `cpu.weight`), CFS throttling counters (`nr_throttled`, `throttled_usec`), initialization duration, and container restart count. | "Test pod", "dummy app". |
| **Deferred In-Place Resize (`ResizeDeferred`)** | The state when an in-place vertical scale-up (`kubectl resize` or VPA `InPlaceOrRecreate`) cannot be immediately admitted by `kubelet` because the node lacks sufficient free allocatable capacity; `kubelet` sets `PodResizePending=True` (`reason: Deferred`) and emits a `ResizeDeferred` event while the container continues running at its current allocation (`restartCount: 0`). | "Failed resize", "resize crash". |
| **Scheduler Preemption for In-Place Pod Resize (`InPlacePodVerticalScalingSchedulerPreemption`)** | Kubernetes 1.37 capability (KEP-5836) where `kube-scheduler` (or the priority preemption controller on Standard non-alpha clusters) watches Pods with `PodResizePending: Deferred`, calculates the resource delta (`Desired - Allocated`), and preempts lower-priority Pods (`PriorityClass`) on the same node so the high-priority Pod completes its in-place scale-up (`ResizeCompleted`) with zero restarts. | "Node drain", "Pod replacement". |
| **VPA Deferred Resize Fallback (`EvictedByVPA`)** | GKE VPA `InPlaceOrRecreate` fallback behavior where an in-place resize that remains in `PodResizePending: Deferred` for more than 5 minutes (or `Infeasible` for more than 1 minute) falls back to Pod eviction (`reason=EvictedByVPA`) so the Pod can be rescheduled onto a node with sufficient capacity. | "Permanent resize hang". |
| **Reclaimed Slack Bin-Packing** | Co-locating low-priority batch or scavenger Pods (`PriorityClass: low-priority-batch`) into the node CPU headroom freed when VPA rightsizes an over-provisioned serving Pod (`PriorityClass: high-priority-serving`) downward in place, raising node CPU request utilization above 90% while preserving fast scale-up headroom via priority preemption. | "Node overcommitting". |
